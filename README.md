# KV Cache 分页块分配器（kv-block-allocator）

**学习目的：搞清楚 vLLM 是如何管理 KV Cache 的** —— 用纯 Python 从零复现其分页块分配的核心机制，并以朴素版对拍验证正确性。

> vLLM 生产级的 KV cache manager 当然远比这复杂——引用计数、写时复制、前缀缓存、抢占恢复——但它的初版内核就是这个分配器：显存切块、块表索引、申请与释放。先把这一层做对，再逐层加复杂度。造轮子没那么可怕，每个人都是从这里开始的。

- 核心：空闲块池 + 引用计数 + 写时复制
- 背景：把KV Cache从[一条序列一段连续显存] 改成 [固定大小的块 + 块表], 碎片问题就变成一个纯粹的分配器问题。
- 难点：不在于block的分配，而是fork之后如何共享，也即是说，当一块显存被多条序列引用时，谁来决定它什么时候可以回收。 其实这里比较有意思的点，是这个思想类似于cpp种的智能指针，用来管理这个块的生命周期。那么这里也会有坑，如果没有正确管理这里的引用计数，就会踩到别人的显存。

## 规格契约
- 显存被切成num_block个块，每块能装block_size个token的KV
- 每条序列有一张块表，记录它按顺序用了哪些块
- allocate要么完整成功，要么完全不改状态-不允许分配到一半还留下半张块表
- fork让子序列共享父序列已有的块（主要是prefix复用，当然，beam search也靠它），共享块的引用计数加一
- free把引用计数减一，减到0才真正回到空闲池

## 核心问题
- 怎么保证块表和实际物理显存块的一致性？
- 怎么提高块的分配效率？不允许每次分配遍历已有块表，块表也可能会很大
- 块表应该按照什么维度维护？是每个attention layer一个？还是要按照序列去维护块表？

## 验收标准
- 空闲块数 + 引用计数大于0的块数 = num_blocks 在任何时刻都成立
- 一个块要么在空闲池里、要么引用计数大于0，不能两者皆是或者两者都不是
- 任何块的引用计数不为负数
- 返回false的调用不允许改变状态
